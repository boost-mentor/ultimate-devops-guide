# Лабораторная 1.8 — контролируемый minor-upgrade

Upgrade не начинается с команды. До запуска фиксируются исходная версия,
состояние API, нод, системных Pod и приложения. У приложения есть несколько
реплик и PodDisruptionBudget. Параллельный HTTP probe считает успешные ответы и
ошибки, а snapshot etcd создаётся и проверяется отдельным playbook.

Порядок:

1. открыть `app/deployment.yaml` и `app/pdb.yaml`;
2. запустить симметричные проверки «до»;
3. открыть и объяснить `playbooks/etcd-snapshot.yml`;
4. создать snapshot и проверить его status;
5. запустить `scripts/http-probe.sh` в отдельном терминале;
6. сравнить файлы в `versions/`;
7. открыть официальный `upgrade-cluster.yml` и импортируемый playbook;
8. выполнить upgrade только при зелёных preflight-проверках;
9. повторить те же проверки «после» и прочитать счётчики probe.

Слепой повтор после ошибки запрещён. Сначала читается первая упавшая task и
проверяется состояние ноды/кластера.

Файлы `versions/k8s-cluster-1.34.7.yml` и
`versions/k8s-cluster-1.35.4.yml` совпадают во всём, кроме одной строки
`kube_version`. Это проверяется обычным `diff -u` до копирования целевого файла.
Обновление идёт только на соседнюю minor-версию, которую поддерживает тот же
зафиксированный release Kubespray; произвольный номер не подставляется.

Snapshot playbook по умолчанию останавливается, если файл уже существует. Для
осознанного перезапуска лабы передают `allow_snapshot_retake=true`: удаляется
только заранее проверенный путь `/var/backups/etcd/video2-pre-upgrade.db`, после
чего новый snapshot обязательно читается `etcdutl snapshot status`. Это
удобство retake, а не production backup policy: production snapshot получает
уникальное имя, шифрование, off-host copy и проверяемый restore drill.
