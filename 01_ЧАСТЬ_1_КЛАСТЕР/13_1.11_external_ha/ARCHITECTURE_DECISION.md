# External HA — решение до реализации

## Что существует сейчас

`10.77.0.10` — VIP внутренней учебной L2-зоны между `lb1` и `lb2`. Эта
зона строится поверх VXLAN и не является автоматически достижимой с ноутбука
или из Интернета. Поэтому называть этот адрес публичной точкой входа нельзя.

## Модель демонстрации Part 1

В Part 1 VIP доказывает автоматический выбор одного активного балансировщика
внутри пары. HTTP через VIP проверяется с `lb1/lb2`, где L2-зона достижима.
Отдельно с ноутбука открывается SSH local-forward на активный балансировщик для
показа приложения и HAProxy stats. Туннель — транспорт записи, а не часть
production-архитектуры.

## Что нужно для внешнего production-входа

Нужен адрес или маршрут, достижимый клиентом: provider floating IP, routed
public prefix/BGP, внешний cloud LB либо VRRP в реальной общей L2-сети. Выбор
зависит от платформы. VXLAN между двумя VM сам по себе эту задачу не решает.

## Что реализовано в source

- один канонический `playbooks/site.yml`;
- VXLAN восстанавливается persistent systemd unit после перезагрузки;
- Ansible `template.validate` проверяет временные HAProxy/keepalived configs до
  атомарной замены live-файлов;
- handlers выполняют reload, а keepalived проверяет реальный `/readyz` через
  HAProxy, не только состояние процесса;
- stats слушает только loopback и открывается через SSH tunnel;
- `scripts/failover-probe.sh` пишет timestamps и максимальную серию ошибок;
- решение про API находится в Terraform `API_ENDPOINT_DECISION.md`.

## Runtime gate перед полной HA-сценой

Source не заменяет проверку на живых VM. До записи нужно доказать: private
routes до всех NodePort, ровно один владелец VIP на `vxlan100`, рост backend
counters в stats, смену владельца после остановки активного HAProxy, HTTP
recovery и фактическую длину разрыва. Если VIP не переезжает, отдельно проверяют
interface, VRRP traffic и асимметричный маршрут; firewall — лишь одна гипотеза.
